## 整体流程

- 1.window因为输入、动画、`invalidate()`、`requestLayout()`、Insets 或窗口变化进入下一帧调度；`ViewRootImpl.scheduleTraversals()` 注册VSync
![alt text](image.png)

- 2.`EventThread`发送Vsync的Event，即`vsync-app`信号翻转，主线程经过`DisplayEventReceiver``onVsync`后逐步回调进入`Choreographer#doFrame()`，按 `INPUT ANIMATION INSETS_ANIMATION TRAVERSAL COMMIT` 处理这一帧的所有回调
![alt text](image-1.png)

- 3.`Traversal` 根据window的状态决定是否执行 measure、layout 和 draw；如果走硬件加速绘制路径，则在 `performDraw()` 中通过 `ThreadedRenderer.draw()` 更新 RenderNode / DisplayList，然后到达UI主线程和 RenderThread的同步边界
![alt text](image-2.png)

- 4.UI主线程通过 `HardwareRenderer.syncAndDrawFrame()` 走到 native的`RenderProxy::syncAndDrawFrame()` ->`DrawFrameTask::drawFrame()`->`DrawFrameTask::postAndWait()` 把DrawFrameTask投到RenderThread，UI线程在这等信号
![alt text](image-3.png)

- 5.RenderThread 随后执行 `syncFrameState()`，同步主线程提交的树状态，并准备这一帧需要进行的GPU工作
![alt text](image-4.png)

- 6.RenderThread 通过 `Surface` 从当前 App Window 的 BLAST BufferQueue的Producer端dequeueBuffer；在这里存在返回的slot 的release fence尚未满足时，可能在这一步等待
![alt text](image-5.png)

- 7.RenderThread 通过 Skia 生成并提交 GPU 命令；随 buffer 一起提交的
![alt text](image-6.png)

- 8.RenderThread `queueBuffer()`，把本帧 buffer、producer completion fence 和帧号交给 `BLASTBufferQueue`，`QueuedBuffer - VRI`信号在此+1。同时，GPU completion fence 会在Consumer 侧作为 acquire fence，表示 Consumer 何时可以安全读取这块 buffer，即`queueBuffer()` 返回时 GPU 工作可能仍未完成
![alt text](image-7.png)

- 9.App 进程内的 BLAST Consumer acquire `BufferItem`，调用 `Transaction::setBuffer()` 并 `apply()`，将 buffer 更新通过 Binder 发送到 SurfaceFlinger。SurfaceFlinger 将有效 buffer transaction 计入 pending 后，`BufferTX - <layerName>` counter +1
![alt text](image-8.png)

- 10.SurfaceFlinger 内的Timer到时触发MessageQueue的vsyncCallback， `vsync-sf` 信号翻转，发送消息给SurfaceFlinger主线程，SurfaceFlinger后续进入`onFrameSignal`流程
![alt text](image-9.png)

- 11.SurfaceFlinger在`onFrameSignal`中进入commit流程，SurfaceFlinger在其中应用事务，latch buffer，选择刷新率等。
![alt text](image-10.png)

- 12.commit流程没有问题，正式进入composite合成上屏流程。SurfaceFlinger把整屏可见Layer交给HWC协商，HWC决定哪些Layer交给硬件Device合成，哪些必须给GPU进行Client合成
![alt text](image-11.png)

- 13.HWC 完成显示提交后，将 present Fence 返回给 SurfaceFlinger，用于跟踪本次显示操作的呈现完成时机。SurfaceFlinger 则根据 buffer 的使用情况及对应的 release Fence，在满足释放条件后，通过APP端 releaseBufferCallback 通知相关组件释放 Buffer。`BLASTBufferQueue`处QueuedBuffer-1

注意，present Fence关注的是本次显示何时完成呈现，release Fence关注的是buffer何时可以安全复用，两者在时间上接近，但是关注的事件与signal的条件不同
![alt text](image-12.png)



## s1
invalidate()表示某个区域的显示内容失效，标记脏区域，调度traversal
requestLayout()表示当前 View 的测量结果或位置可能失效，向父级传播布局请求，调度traversal
ViewRootImpl框架不会马上递归遍历整棵树。ViewRootImpl.scheduleTraversals()通过mTraversalScheduled避免重复调度，并把遍历回调交给Choreographer,这里的mTraversalScheduled可以保证在一次Vsync信号来之前只会通过FrameDisplayEventReceiver向EventThread标记申请一次Vsync信号，即多次对view的修改都被合并到了一次Vsync信号中来处理

## s2
Choreographer把input，animation和traversal回调放到统一的帧节拍，按照
CALLBACK_INPUT
CALLBACK_ANIMATION
CALLBACK_INSETS_ANIMATION
CALLBACK_TRAVERSAL
CALLBACK_COMMIT
的顺序执行，input，animation，insets_animation阶段会对view的状态和属性进行更新，后续由traversal读取这些变化结果进行performTraversals()

## s3
ViewRootImpl.performTraversals()是窗口级遍历的核心入口。根据view的状态选择性执行measure，layout，draw
硬件加速绘制时的每一个view都有一个RenderNode，一个RenderNode内部持有DisplayList，还保存了一组渲染属性，view的绘制内容就存放在这个RenderNode的DisplayList中，View树对应为一棵RenderNode树
View绘制时，通过RecordingCanvas记录绘制指令，绘制指令被记录到对应RenderNode的DisplayList中，之后准备移交RenderThread

## s4
UI主线程完成录制后，RenderNode树通过syncAndDrawFrame()被同步给RenderThread，RenderThread遍历这棵RenderNode树，对每个节点取出其DisplayList，把其中绘制指令翻译成GPU能执行的图形指令
